# preflight — استاندارد بررسی سرور

`deploy/preflight.sh` می‌پرسد **«آیا این سرور همان‌طور که گفتیم راه‌اندازی شده؟»**
و هرجا نشده، دستور دقیق رفعش را کنارش می‌نویسد. چیزی را عوض نمی‌کند و هیچ رازی
چاپ نمی‌کند.

این با `watchdog.sh` فرق دارد: دیده‌بان هر پنج دقیقه می‌پرسد «الان چیزی خراب
است؟». این یکی می‌پرسد «از اول درست ساخته شده؟» — سؤالی که بعد از نصب، بعد از
هر تغییر سرور، و هر چند وقت یک‌بار ارزش پرسیدن دارد.

```bash
deploy/preflight.sh                    # بررسی کامل
deploy/preflight.sh --full             # به‌علاوه‌ی بررسی‌های کند
deploy/preflight.sh --list             # بخش‌ها
deploy/preflight.sh --only tls,backup  # فقط چند بخش
deploy/preflight.sh --quiet            # فقط مواردی که نیاز به توجه دارند
```

خروجی: `0` وقتی هیچ `✗` نباشد، `1` وقتی باشد — پس در کرون هم قابل استفاده است.

## اضافه کردن یک بررسی

داخل هر فایل، فقط از توابع زیر استفاده کنید:

```bash
section "۴۲ — عنوان بخش"

ok   "چیزی که درست است"
warn "چیزی که بد است ولی سیستم را نمی‌خواباند"  "دستور رفعش"
bad  "چیزی که باید همین حالا درست شود"          "دستور رفعش"
skip "چیزی که قابل بررسی نبود"
note "متن کمکی — شمرده نمی‌شود"
```

و از این کمکی‌ها:

| تابع | کار |
|---|---|
| `have <cmd>` | آیا این دستور نصب است |
| `env_get KEY` | خواندن یک کلید از `.env` |
| `secret_ok KEY 32` | راز هست و حداقل ۳۲ کاراکتر است (مقدارش را چاپ نمی‌کند) |
| `svc_state <service>` | وضعیت کانتینر compose |
| `compose_ids` | شناسه‌ی همه‌ی کانتینرها |
| `db_query "SELECT …"` | یک کوئری داخل کانتینر دیتابیس |
| `http_code <curl args>` | کد پاسخ HTTP با تنظیمات درست TLS |
| `age_hours <file>` / `age_days <file>` | سن فایل |

### سه قاعده‌ای که رعایتشان مهم است

**۱. هر `warn` و `bad` باید دستور رفع داشته باشد.**
گزارشی که می‌گوید چیزی خراب است ولی نمی‌گوید چطور درست شود، فقط اضطراب تولید
می‌کند.

**۲. حلقه‌ی خالی نباید تیک بزند.**
اگر روی چیزی حلقه می‌زنید، اول تعدادش را بشمارید. حلقه‌ای که روی صفر مورد اجرا
شود هیچ تخلفی پیدا نمی‌کند و `✓` می‌زند — و این بدترین اتفاق ممکن در یک ابزار
بررسی است، چون باورش می‌کنند. (یک بار در همین پروژه، «هیچ شماره‌ای در ۰ آگهی لو
نرفت» به‌عنوان موفقیت گزارش شد.)

**۳. یک علت، یک گزارش.**
اگر وب‌سرور خوابیده، بررسی هدرها را `skip` کنید نه `bad`. وگرنه یک خرابی واقعی
زیر دوازده خرابی ساختگی دفن می‌شود — و یکی از آن دوازده‌تا ممکن است `✓` باشد که
سرور به دست نیاورده.

## انتقال به پروژه‌ی بعدی

```bash
cp -r deploy/preflight.sh deploy/preflight.d/ ../new-project/deploy/
cd ../new-project
rm deploy/preflight.d/55-behaviour.sh deploy/preflight.d/60-data.sh   # مال پروژه‌ی قبلی
```

بعد بالای `preflight.sh` (یا در `deploy/preflight.conf` که کامیت نمی‌شود) این‌ها
را عوض کنید:

```bash
PROJECT_NAME="نام پروژه"
PROJECT_SLUG="project"            # نام فایل‌های کرون، پوشه‌ی بکاپ
SERVICES="db api web"
OPTIONAL_SERVICES=""
API_PREFIX="/api/v1"
EXPECTED_PORTS="22 80 443"
FORBIDDEN_PORTS="5432 3000"
REQUIRED_SECRETS="POSTGRES_PASSWORD:16 SESSION_SECRET:32 JWT_SECRET:32"
EXPECTED_FILES="frontend/index.html docker-compose.yml"
```

و دو فایل جدید برای رفتار و داده‌های آن پروژه بنویسید. بقیه‌ی بخش‌ها همان‌طور
که هستند کار می‌کنند.
